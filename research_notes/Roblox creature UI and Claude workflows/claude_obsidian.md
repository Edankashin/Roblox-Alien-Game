## Key question 1: What vault layouts do experienced users recommend for a game project, and what do they say to avoid?

### Takeaway
Every credible 2026 setup converges on the same shape: a small set of numbered or purpose-named folders, one hub/map-of-content per area, a daily append-only log, a decisions record with a status field, templates, frontmatter on every note, and a `CLAUDE.md`/`AGENTS.md` at the root that is the "schema" telling the agent how the vault is organised. The named anti-patterns are deep folder trees, unrestricted agent write access to a large vault, unlinked pages, a bloated CLAUDE.md, and treating the vault as a dump rather than a compiled, linked wiki.

What to avoid:
- Keep folders minimal: "Most people create hundreds of folders and spend more time organizing notes than actually using them." — [MindStudio guide](https://www.mindstudio.ai/blog/build-ai-second-brain-claude-code-obsidian) (snippet)
- Unrestricted write access: an author pointed Claude at a 3,214-note vault with no backup and found 340 files changed; the fix was restricting tags to a fixed list; reading a large vault burns usage quota, so scope Claude to folders. — [Medium, trends24](https://medium.com/@trends24/i-pointed-claude-at-my-3-214-note-obsidian-vault-4-months-ago-heres-why-that-was-a-big-mistake-88636e7b8825) (snippet)
- Don't open a code repo as a vault (clutters the explorer); use a separate developer vault with symlinks when the vault must sit beside code repos. — [StarMorph guide](https://blog.starmorph.com/blog/obsidian-claude-code-integration-guide) (snippet)
- Don't move existing topic directories into a `wiki/` subfolder: "Your existing directories ARE the wiki"; moving breaks wikilinks and Dataview. — [jhinpan gist](https://gist.github.com/jhinpan/16f240dfce4b45532f28b5df829bc887)
- "Nothing is ingested until it is linked"; "A page that lands unconnected is invisible within a week"; "Contradictions are recorded, never overwritten"; "No vector database until you need one"; counterpoint quoted by the same repo: "if the writing is the thinking, delegating it means not doing it." — [second-brain-os](https://github.com/undefined-ui/second-brain-os)
- Over-long CLAUDE.md: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; `/doctor` proposes cuts for content derivable from the codebase. — [Claude Code memory docs](https://code.claude.com/docs/en/memory); "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" with an include/exclude table (include commands Claude can't guess, style rules that differ from defaults, gotchas; exclude anything derivable from code, API docs, frequently changing info). — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- The Karpathy stack adds a "Dangerous or Embarrassing Test" to decide what goes in always-loaded rules versus on-demand wiki pages, a rule to split hubs with more than 15 members, a ~500-word `wiki/hot.md` read at session start, and a single-writer rule. — [ScrapingArt/Karpathy-LLM-Wiki-Stack](https://github.com/ScrapingArt/Karpathy-LLM-Wiki-Stack)

### Inferences
- The owner's current `docs/vault` layout (00 start-here through 08 log, hub per folder, glossary, refs folder, playbook, decisions table) is a faithful copy of the cuhfilme reference and matches the general pattern; what the general pattern adds that cuhfilme's video does not show is a templates folder, per-decision records with a status field, a tiny always-loaded "hot" file, and a Dataview/Bases dashboard driven by frontmatter.
- For a game project specifically, the mapping is: `raw/` = reference videos, screenshots and research reports; `wiki/` = engine facts, UI playbook, art rules, design notes; `decisions/` = the product and build decisions; the daily log = the session log. The project already has all four, under different names.

## Key question 2: Which Obsidian-to-Claude connections exist in 2026, what each can do, and what they cost?

### Takeaway
Five routes exist: (1) the plain filesystem from Claude Code (zero setup, works with Obsidian closed and in cloud sessions, no graph awareness); (2) the official Obsidian CLI (v1.12, Feb 2026) plus Obsidian's own `obsidian-skills` pack (search, backlinks, daily-note append, properties; needs the app open); (3) MCP servers over the Local REST API plugin (read/write/patch-by-heading/search/tags/commands; needs the app open and an API key; the plugin now ships its own MCP endpoint); (4) MCP servers that read the folder directly (bbdaniels/obsidian-mcp, administrativetrick); (5) Claude living inside Obsidian (Claudian, Roasbeef's Agent-SDK plugin, iansinnott's IDE bridge). Token cost is dominated not by the connection but by what gets loaded: tool schemas are deferred by default in Claude Code, while every file read costs 1–3k tokens.

### Cited Findings

Filesystem (Claude Code reads the vault as files):
- "Claude Code has one fundamental problem: it forgets everything between sessions"; the vault is the persistent memory; run `/init` inside the vault to generate a starter CLAUDE.md; the usual approach is to open Claude Code from the vault folder so `.claude/skills/` and `CLAUDE.md` load. — [dev.to, mibii](https://dev.to/mibii/claude-code-obsidian-build-a-second-brain-that-actually-thinks-d61) (snippet); [az9713/claude-code-obsidian](https://github.com/az9713/claude-code-obsidian)
- "Writing `.md` files straight to disk works without Obsidian open. Obsidian's file watcher picks those changes up on next launch, so they may not appear in an open app right away." — [az9713/claude-code-obsidian](https://github.com/az9713/claude-code-obsidian)
- A 2026 guide notes the generic Filesystem MCP server also works with Obsidian closed because a vault is just a folder of `.md` files. — [MCP Bundles guide](https://www.mcpbundles.com/blog/obsidian-mcp-vault-ai) (snippet)

- Anthropic's guidance: just-in-time agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and read on demand, versus pre-loading; "runtime exploration is slower than retrieving pre-computed data"; the goal is "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome." — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences
- For this team the filesystem route is the only one every session can use: the cloud coordinator and build workers have no Obsidian process, so anything that depends on the CLI or the REST API is Mac-only convenience. The CLI is worth turning on for the Mac session (backlinks and daily-append without touching files) but it cannot be the primary channel.
- MCP over REST adds ~15 tool definitions; with Claude Code's deferred tool schemas the standing cost is small, but it gives nothing the filesystem lacks for a vault that is already linted and hub-linked. Its real wins are heading-targeted PATCH and search-by-frontmatter for the Claude desktop app, which cannot read files directly.

## Key question 3: How do people use the vault during a session (start, during, end), and how do they enforce it (hooks, lints, templates)?

### Takeaway
The mature pattern is: at start, a hook or the CLAUDE.md loads a tiny hub (goals, active work, recent log, drift flags) under a byte budget; during, the agent appends to today's daily note and links; at end, a wrap-up skill or Stop hook moves lasting findings into topic notes, validates frontmatter and wikilinks, and commits. Enforcement moved in 2026 from "instructions in CLAUDE.md" (advisory; Anthropic's own docs say so) to hooks (deterministic), with a read-only lint script as the ground truth because "you can't trust an agent's self-reporting on link integrity".

### Cited Findings

What is advisory vs enforced (official):
- "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [Memory docs](https://code.claude.com/docs/en/memory)
- "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." "Use hooks for actions that must happen every time with zero exceptions." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Hook events include `SessionStart` (sources `startup`, `resume`, `clear`, `compact`, `fork`; stdout goes into Claude's context; can set `additionalContext`, `initialUserMessage`, `watchPaths`, `reloadSkills`), `UserPromptSubmit` (can inject `additionalContext`), `PostToolUse` (after Edit/Write, can `block`), `Stop` (exit 2 keeps Claude working), `SubagentStop`, `TaskCompleted`, `PreCompact`/`PostCompact`, `InstructionsLoaded`, `FileChanged`; handler types `command`, `http`, `mcp_tool`, `prompt`, `agent`; hooks live in `~/.claude/settings.json`, `.claude/settings.json` (shareable), `.claude/settings.local.json`, plugin `hooks.json`, or skill/subagent frontmatter. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Official example of re-injecting context after compaction: a `SessionStart` hook with `"matcher": "compact"` whose command echoes reminders, "replace the echo with any command that produces dynamic output, like `git log --oneline -5`"; for every-session context "consider using CLAUDE.md instead." — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- What survives compaction: project-root CLAUDE.md and unscoped rules, auto memory and the plan-mode plan are re-injected from disk; up to five recently modified files are re-read (files over 5,000 tokens come back as a path reference); "Context that hooks added earlier" is summarized away; SessionStart hooks matching `compact` run again. — [Context window page](https://code.claude.com/docs/en/context-window)
- Path-scoped rules: `.claude/rules/*.md` with `paths:` frontmatter load only when Claude works with matching files; they load on demand and are summarized away at compaction. — [Memory docs](https://code.claude.com/docs/en/memory)
- A Stop hook can gate the turn's end: "a Stop hook runs your check as a script and blocks the turn from ending until it passes. Stop input covers the cap on consecutive blocks." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Verification principle: "Give Claude a check it can run... Have Claude show evidence rather than asserting success." — [Best practices](https://code.claude.com/docs/en/best-practices)

## Key question 5: How should a two-person team with a cloud coordinator session, a Mac session and workers use one vault without conflicts?

### Takeaway
Practitioners who share a vault across people and agents all land on: one writer per note at a time, append-only daily notes with per-session headings, lasting notes edited in small commits, git as the only cross-account channel (file-sync tools must exclude `.git`), frontmatter `owner`/`status` so views can be regenerated instead of hand-merged, and personal files kept out of the shared tree (`CLAUDE.local.md`, workspace files). Claude's own 2026 features reinforce this: auto memory and Projects memory are machine- or account-local, cross-session messaging works only within one account, and cloud sessions clone from GitHub.

### Cited Findings
- Team vault: members share through Syncthing "hub-and-spoke" with an always-on machine running "the nightly git snapshot, summaries and cleanup"; "A vault is not a git checkout": only the automation host keeps a repository; `external-projects/` is excluded from sync ("use github here instead"); "Everything needs exactly one owner"; to get someone else's work, create a subtask they own and keep yourself as reviewer; "Everyone sees everything, so keep sensitive material out"; conflict copies are hidden by Bases views, so search for them periodically, merge and delete. — [SimonSkade1/obsidian-team-vault](https://github.com/SimonSkade1/obsidian-team-vault) (conflict-copy sentence from search snippet)

## What the Claude desktop app and Claude Code offer natively in 2026 that overlaps, and when a vault still wins

### Takeaway
Native memory in 2026 is layered and real: claude.ai/desktop memory (topics, per-project, editable, importable), Claude Code auto memory (per-repo, machine-local, `MEMORY.md` index), Claude Projects memory (per-project files read by cloud threads), CLAUDE.md and `.claude/rules/`, skills, and hooks. Each is scoped to one account, one machine or one product surface and none is reviewable in git. A vault wins when the memory must be shared across accounts, machines and tools, be diffed and reviewed, hold rich artefacts (screenshots, hex tables, pipelines), and be enforced by lints; native features win for personal preferences and corrections and for always-on rules.

### Inferences
- Auto memory and the vault overlap on "corrections you give Claude"; the documented behaviour that auto memory skips what CLAUDE.md already says means the cheapest division is: standing rules in CLAUDE.md (pointing at the vault), lasting team facts in the vault, personal quirks left to auto memory. Anything the Mac session's auto memory learns that matters to the coordinator or the collaborator must be copied into the vault by hand, because nothing else carries it across.
- claude-mem is a per-Mac transcript memory, not a team memory; it does not feed the vault. If the team wants automatic lesson mining into markdown, memem-style tools write into an Obsidian folder, at the price of extra Haiku calls.

## Judgement of the current setup against the best practitioners, and the gaps

### Takeaway
The repo already has the hard parts: a vault inside the repo with cuhfilme's layout, hubs, frontmatter, a glossary, a UI playbook with refs, a decisions table, a per-day log with per-session headings, a 51-line CLAUDE.md that points at the vault, a standard-library lint that fails CI on broken links, Board-based claiming and git as the sync channel. What it lacks, relative to 2026 practice, is enforcement (no hooks), templates and per-decision status records, a small always-loaded "hot" note, staleness and ambiguity checks, path-scoped rules that pull the playbook in when UI files are touched, and a settled stance on auto memory and claude-mem.

### Cited Findings (current state, from the repo)
- `CLAUDE.md` is 51 lines and contains the "Vault logging" rules: one dated note per day in `docs/vault/08-log/`, a heading per session, "Append; never rewrite another session's lines", lasting facts move to topic notes with `[[Note-Name]]` links, no secrets in the vault. — `repo: CLAUDE.md` (line count from `wc -l`)
- `docs/vault/README.md` house rules: frontmatter `tags` (folder topic plus one or two of `pipeline`, `decision`, `research`, `ui`, `engine`, `log`, `plan`, `species`), `aliases`, `up` linking the hub; at least one link in and one out; a new note goes into its hub in the same change; `python3 -I tools/lint_vault.py` checks it and runs inside `tools/lint.sh`. — `repo: docs/vault/README.md`

### Inferences (the gaps, ranked by value for this team)
1. Enforcement: add a `.claude/settings.json` `hooks` block checked into the repo so every session (cloud, Mac, workers, the collaborator's Claude) gets it: `SessionStart` (matchers `startup|resume|compact`) that prints a short budgeted digest (Launch-Dashboard headline, open Board rows claimed by nobody, today's log headings, `git log --oneline -5`); `PostToolUse` on `Edit|Write` matching `docs/vault/**/*.md` that runs `python3 -I tools/lint_vault.py`; a `Stop` hook that exits 2 with a message when `git diff --name-only` shows `src/` changes but no change under `docs/vault/08-log/` or `docs/vault/`. Grounds: Anthropic's "advisory vs deterministic" language, the compaction table (hook context is summarised away, so a `compact` matcher is needed), obsidian-mind's zero-vault-calls test.
2. A small "hot" note: a ~300–500-word `00-start-here/Now.md` (or trim Launch-Dashboard to that) listing the five things a session must know today, linked from CLAUDE.md, so sessions stop paying for the 52 KB Handoff on every start; keep Handoff as the on-demand background. Grounds: HOT-tier budgets (≤2,400 tokens; ~500 words; ~120 tokens) and Anthropic's just-in-time guidance.
3. Path-scoped rules that pull vault notes in when relevant: `.claude/rules/ui.md` with `paths: ["src/client/**"]` saying "read `docs/vault/05-ui-design/UI-Playbook.md` and `UI-Checklist.md` before editing; Scale not Offset; theme module"; similar rules for `src/shared/data/**` (data tables, odds sum to 100) and `assets/models/**` (art pipeline notes). Grounds: path-specific rules in the memory docs; "read it before UI or asset work" is currently advisory in CLAUDE.md.
