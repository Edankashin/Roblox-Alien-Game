## Key question 1: What is Claude Design today, and can it draw orthographic or isometric sheets of blocky characters that a 3D build can follow?

### Takeaway
Nothing material changed since the 2026-10-15 notes: Claude Design is Anthropic's canvas of HTML artboards (in-chat since 2026-09-16, out of beta 2026-10-08), it does not generate raster images, and no first-party page or public example shows it making character turnarounds, orthographic views or game creature concepts. It can nevertheless draw an exact orthographic sheet of a blocky creature, because a blocky creature's front, side and top views are just rectangles: the Design type's own rules allow an illustration as one inline `<svg>` and dimension labels as separate placed elements, which yields a measured, stud-gridded drawing that a box modeller can follow better than a painted concept. Isometric views are possible in principle (SVG projection maths or CSS 3D transforms) but undocumented and untested.

### Inferences
- A blocky creature is the best case for Claude Design among character styles: its orthographic views are axis-aligned rectangles with hex fills, which SVG draws exactly. A sheet drawn this way is a measured drawing (every block's width, height and offset readable off a stud grid), the property a box modeller needs and a painted concept lacks.
- The sheet should be generated from the creature's numeric spec (a parts table, see key question 2) rather than drawn freehand, so the drawing and the build read the same numbers. Two routes, both untested: (a) Claude writes the SVG from the spec when it writes the artboard (works within the documented rules); (b) the spec is uploaded as a `.json` asset, fetched in the artboard's logic and rendered through `{{holes}}` and `<sc-for>` repeats; whether `<sc-for>` works inside an `<svg>` is not documented.
- Isometric or three-quarter previews: an isometric box is three parallelograms whose corners follow from 30-degree projection, so Claude can compute them into SVG polygons; CSS `transform: rotateX/rotateY` with `preserve-3d` is another route. A live three.js viewer would need three.js uploaded as a `.js` asset and drawing into a canvas, which sits awkwardly with "never script-built"; treat it as out of bounds until tried. The cheaper three-quarter view is a Blender render uploaded as an image, which the brief already does for turnarounds.
- What it should not be asked for: painterly concept art, face textures as paintings, or VFX frames as raster art; those are either Blender renders placed on the board or pixel grids drawn as SVG rects (a face texture at 8x8 or 16x16 pixels is 64 or 256 rects, trivially exact).
- Rarity ladders and VFX mock-ups suit it: a ladder is the same base figure repeated with added blocks, height and an emissive overlay per tier; a VFX mock-up is an SVG burst or a CSS-animated artboard with `data-props` sliders for timing, which the earlier notes already showed the canvas supports.

### Gaps
- No first-party statement on whether Design artboards may use CSS 3D transforms, `<canvas>` drawing or `<sc-for>` inside SVG; each needs one test artboard.
- No public example, from Anthropic or users, of Claude Design producing character model sheets; whether it handles 30+ part sheets without misaligning parts is unknown until tried.
- The June "2.0" update is single-sourced.

## Key question 2: How do artists go from a 2D orthographic sheet to a box-modelled blocky character in Blender or Blockbench, and what does a good blocky turnaround sheet contain?

### Takeaway
The standard method is unchanged since the 1990s: front, side and top views drawn at one scale on a shared grid, loaded as image planes in matching orthographic views, then boxes placed to the outlines. Blockbench has this built in as "blueprint" reference images that attach to one orthographic side and show only in that view. What is new in 2026 is tooling that closes the loop numerically: two open-source MCP servers now drive Blockbench (one with 70 tools, a silhouette-match score against a reference, measured proportions and a cube-count "density gate"; one that edits `.bbmodel` files headless, without Blockbench running), and a Blender MCP fork scores silhouette IoU between an orthographic render and a reference image. For a blocky creature the sheet should be a measured drawing plus a parts table in studs, so the build can be scripted from the table and checked against the drawing.

### Cited Findings

- `ReferenceImageViewMode = 'flat_image' | 'blueprint' | 'plane'`; layers `'background' | 'viewport' | 'float'`; scopes `'project' | 'global' | 'built_in'`; per-image `opacity`, `flip_x`, `flip_y`, `clear_mode`, `attached_side`, and `sync_to_timeline` (video files `mp4`, `wmv`, `mov` are accepted as references) **(read)** — [blockbench js/preview/reference_images.ts](https://github.com/JannisX11/blockbench/blob/master/js/preview/reference_images.ts)
- A blueprint is drawn only when an orthographic preview faces its side: `Preview.all.some(p => p.isOrtho && p.angle == this.attached_side)`; adding an image while an orthographic view is selected switches it to blueprint mode on the background layer automatically; `plane` mode places it on a side (`-z`, `+z`, `-x`, `+x`) offset by the format's block size **(read)** — [reference_images.ts](https://github.com/JannisX11/blockbench/blob/master/js/preview/reference_images.ts)

### Inferences
- The bevel numbers decide the blocky look's budget. Six-segment bevels on every cube (the 2020 tutorial) cost 588 triangles a cube, so only four such cubes fit in 2,500. Plain cubes cost 12, so the MCP's "mob" budget of 180 cubes is 2,160 triangles, inside the cap. The workable rule: bevel only the two to four big masses (body, head) at 1 or 2 segments (44 or 108 each), keep every detail block plain, and fake small bevels with a painted edge highlight in the pixel texture (0 triangles). Note that touching cubes keep their hidden faces unless merged, so the count is per cube.
- Cube count is a natural, countable "detail" axis for B43's "rarer aliens get more detail": the MCP's own ladder (prop 30 to 60, mob 100 to 180, hero 180 to 300+) maps onto tiers, but the top of it exceeds the triangle cap unless high tiers use plain cubes or merged meshes. This is a recommendation to test, not a sourced standard.
- A good blocky turnaround sheet for this project, built from the sources above:
  1. Four orthographic views (front, right side, top, back) at one scale, feet on a shared baseline, front facing the viewer as -Z (Blockbench and Roblox front), plus one three-quarter view (a Blender render, or a computed isometric).
  2. A stud grid: major line every 1 stud, minor every 0.25 stud; the total height in studs printed beside the side view (B43's height step per tier is read here).
  3. A parts table (the real handoff): part name, size w x h x d in studs, min corner or centre, pivot, rotation in degrees, bevel (width and segments, or "painted"), mirror pair (L/R), material slot, colour hex. The drawing is generated from this table.
  4. The palette: each hex with a role (body, belly, accent, emissive) and the rarity overlay (which parts glow or change per tier).
  5. The face as a pixel grid at the texture density (for example 16 px per stud face, the Blockbench default block resolution; an inference), with eye position measured from the head's front face.
  6. A greyscale silhouette strip at thumbnail size (the design doc's existing rule), and the budget line: cube count, triangle estimate from the bevel table above, texture size.
- The build loop then needs no image interpretation: Claude (headless bpy in the cloud, or the Blockbench MCP on the Mac) builds from the parts table, and the image is used only to check, with an orthographic silhouette IoU per view (the `compare_reference` / `blender_compare_ref` idea, easy to reproduce in bpy with a mask render). A per-view threshold such as 0.9 would be a starting guess; no source gives one.
- The vault's Model-Toolchain note says "Blockbench itself has no command line or headless mode". That stays true of the app, but a third-party headless server now creates, edits, validates and renders `.bbmodel` files; for glTF the desktop app (or the project's own Blender route) is still needed, and the headless renderer wants a GPU, which the cloud container probably lacks.

## Key question 3: What do game teams put in a style bible for a creature or pet roster, with real examples?

### Takeaway
Published studio guides converge on four things a roster bible must fix with rules rather than adjectives: silhouette (readable at thumbnail size, one distinguishing trait per type), value and colour (a 5 to 7 colour palette with meanings, value contrast ahead of hue, colourblind backups), detail hierarchy (where detail goes and where the eye rests), and effects whose visual weight matches their gameplay weight. Real examples are older but public: Valve's Dota 2 character art guide (2012), Riot's League VFX style guide (2017, updated by a 2021 clarity post), Roblox's own art-style lessons, and Uplift Games' style guides for Adopt Me merchandise. No Roblox pet game has published its in-game creature bible.

### Cited Findings
- Valve's Dota 2 Workshop Character Art Guide (released June 2012, about 18 pages, hosted on Steam Support) covers silhouette as the first-glance identifier that should also show orientation, value (lightness apart from hue) as often more important than colour, a coherent palette, "rest and detail", and evaluating assets in context, with before-and-after examples **(snippet; 2012, older)** — [Steam Support FAQ](https://help.steampowered.com/faqs/view/0688-7692-4D5A-1935); [CG Channel, 2012](https://www.cgchannel.com/2012/06/valve-releases-useful-character-design-guide)
- A Polycount reading of that guide: if brightness at a hero's feet matches the intensity at the head, the character is harder to read at a glance **(snippet)** — [Polycount](https://polycount.com/discussion/comment/2375439)
- Riot's League of Legends VFX style guide (October 2017) lists four goals, "Provide visual clarity for gameplay, Minimize visual clutter, Promote a champion's theme, Surprise and delight players", pursued through gameplay, value, colour, shape and timing; a big ultimate (Ziggs) is loud and a basic attack (Janna) is quiet, and the two "should not be swapped"; every effect has primary elements (high value range, clear silhouette, strong shape) and subdued secondary ones **(snippet; 2017, older)** — [Riot Nexus: VFX style guide](https://nexus.leagueoflegends.com/en-us/2017/10/dev-leagues-vfx-style-guide/); [Riot VFX style guide PDF](https://nexus.leagueoflegends.com/wp-content/uploads/2017/10/VFX_Styleguide_final_public_hidpjqwx7lqyx0pjj3ss.pdf)
- Riot's 2021 clarity post: projectiles show direction even when still, often with a blurred tail; ability VFX should match hitboxes and follow the game's importance hierarchy **(snippet)** — [Riot: Clarity in League](https://riotgames.com/en/news/dev-clarity-in-league)
- Roblox's UI curriculum: an art style is "visual ground rules"; a colour theme is colours "that each communicate a message through consistent application"; "don't always rely on color alone ... combine colors with icons, shapes, and/or animations"; a "text system" is a set of font rules such as "always bold headers"; icons keep a shape language distinct from the 3D world so their meaning stays distinct **(read)** — [creator-docs: Choose an art style](https://github.com/Roblox/creator-docs/blob/main/content/en-us/tutorials/curriculums/user-interface-design/choose-an-art-style.md)
- Roblox's environment curriculum: choose an art style first as "a main source of truth"; build "a mood or theme board"; props get "only enough geometry that users can tell what a prop is from its silhouette" **(read)** — [creator-docs: Develop polished assets](https://github.com/Roblox/creator-docs/blob/main/content/en-us/tutorials/curriculums/environmental-art/develop-polished-assets.md)
- A Claude Code "game studio" skill pack's `art-bible` skill defines nine sections (Visual Identity Statement, Mood and Atmosphere, Shape Language, Color System, Character Design Direction, Environment Design Language, UI/HUD Visual Direction, Asset Standards, Reference Direction); shape language covers "how readable at thumbnail size? Distinguishing trait per archetype?" and "Hero shapes vs. supporting shapes"; the colour system is "5–7 colors with roles — not just hex codes, but what each color means", semantic colours, per-area temperature, the UI palette's divergence, and "which semantic colors need shape/icon/sound backup"; character direction includes "expression/pose style targets" and "LOD philosophy"; reference direction gives "3–5 reference sources", each with exactly what to take and "what to explicitly avoid" **(read)** — [Donchitos/Claude-Code-Game-Studios art-bible SKILL.md](https://github.com/Donchitos/Claude-Code-Game-Studios/blob/main/.claude/skills/art-bible/SKILL.md)
- Uplift Games (Adopt Me) keeps style guides with on-brand design rules for its consumer products; its core style guide features the most-traded pets plus fan favourites, chosen with a data analyst's numbers **(snippet)** — [Brands Untapped interview with Vicky Huxley and Sim Furniss](https://brandsuntapped.com/?p=8177)
- The project's existing rules that the bible inherits: "every tier must read in greyscale and at thumbnail size", "Keep one goofy thing at every tier"; B43 now replaces "fiercer per tier" with "more detail, more height and more VFX per tier" **(repo)** — [GAME_DESIGN.md section 15](/home/user/Roblox-Alien-Game/docs/GAME_DESIGN.md); [Decisions.md B43](/home/user/Roblox-Alien-Game/docs/vault/07-alien-game/Decisions.md)

### Inferences
- The blocky roster bible, as a set of numbered rules each with a number and a do/don't pair:
  1. Shape language: cubes and cuboids only, edges bevelled only on the two to four main masses (bevel numbers from key question 2); one hero block per species (the exaggerated feature) that no other species in the same world shares.
  2. Proportion: head-to-body ratio and leg length per tier in studs; height steps per tier (B43); all values on a 0.25-stud grid.
  3. Palette: per species one body colour, one belly or face colour, one accent, one emissive; each hex with a role; value contrast checked in greyscale before hue.
  4. Rarity ladder: cube count, height and VFX per tier as a table, following Riot's rule that visual weight tracks importance (a Common gets a sparkle at most; a Legendary gets a persistent aura and particle trail), and the standard rarity colours for any ring or label.
  5. VFX rules: primary versus secondary elements per effect, maximum particle rate per tier for phones, effects never hide the face.
  6. Do and don't sheet: one Claude Design artboard per rule showing a passing and a failing example drawn from the same base figure.
  7. Silhouette test: all species of a world as black silhouettes at 64 px in one row; any two that read alike fail.
- Riot's and Valve's guides are 2012 to 2017 documents for competitive games; their readability rules transfer, their realism and team-colour rules do not.

### Gaps
- No Roblox pet game (Pet Simulator 99, Adopt Me, Grow a Garden, Bee Swarm Simulator) has published an in-game creature style guide or pet design process; the Adopt Me source is about merchandise.
- No GDC talk specific to a collectible creature roster's style guide was found by search this pass; the GDC Vault was not reachable.

## Key question 5: How well does Claude with Blender (MCP or scripted bpy) build from a spec or a reference image as of 2026?

### Takeaway
From a single reference image, Claude-plus-Blender builds come out as assemblies of primitives that miss proportions and curves; with a numeric spec, an orthographic check and a human review gate, they work. That failure mode is the target style here: a blocky creature is primitives by design, so blocky is the style where scripted building is strongest, provided the spec carries the numbers (sizes, offsets, sides) and the image is used only to check. 2026 also brought an official Blender connector for Claude (Blender Lab's MCP server, April 2026, Blender 5.1 or newer), which the project does not need for headless builds.

### Inferences
- What works for blocky creatures: building from a parts table (sizes, positions, pivots, mirror pairs, hexes) in one bpy script, then checking with orthographic renders of four views laid beside the sheet and a silhouette IoU per view. Every number comes from the spec, so the LLM's weak spots (estimating proportions from pixels, keeping left and right straight, judging "enough detail") are replaced by table lookups and gates.
- What still fails and needs a person: taste (whether the face reads cute), the hero block's exaggeration, and VFX feel. Keep the human gate at the board stage (Ethan picks on the Claude Design sheet) and at the render stage (a review line in the spec note).
- Which tool where: cloud workers build and render with headless bpy 5.0.1 from the spec (fits the existing `tools/blender/` scripts); the Mac session uses `mcp-for-blender`'s `look` for a live check, and optionally the Blockbench MCP when a person wants to paint the face texture or keyframe in Blockbench. The official Blender Lab server adds nothing the project needs now; the cloud's bpy 5.0 is below its stated 5.1 floor anyway.
- Do not start a blocky creature from an image-to-3D generator: generators return dense smooth meshes that would have to be rebuilt as blocks, which is more work than building the blocks.

## Key question 6 (the objective): What is the end-to-end workflow so every design passes through Claude Design, Blender and Obsidian?

### Takeaway
Run every asset through one spec note: Obsidian holds the numbers and the verdicts, Claude Design draws the sheet from the numbers for the person to judge, and Blender builds from the same numbers and is checked against the sheet. Concept boards and ladders are reviewed in Claude Design before any mesh exists; renders and verdicts flow back into the note; nothing ships until the note's status is approved, which is B43's "nothing under `assets/models` changes until Ethan says yes to a sheet".

### Cited Findings
- B43: "the route for every design (creatures, props, UI, worlds) is a concept board in Claude Design, a build in Blender, and the spec, decisions and review in the Obsidian vault. Nothing under `assets/models` changes until Ethan says yes to a sheet" **(repo)** — [Decisions.md](/home/user/Roblox-Alien-Game/docs/vault/07-alien-game/Decisions.md)
- Claude Design artboards accept uploaded PNG renders and `.json` data, export each artboard as PNG or PDF, and take comments on elements **(read)** — [Design type SKILL.md](https://claude.ai/artifact/QKN21svewxgyPb6SYRqWnd); [claude_design.md](/home/user/Roblox-Alien-Game/research_notes/Roblox%20creature%20UI%20and%20Claude%20workflows/claude_design.md)
- Obsidian Cards view takes a render or a hex as the card image; Kanban groups by status **(read)** — [Cards view.md](https://github.com/obsidianmd/obsidian-help/blob/master/en/Bases/Layouts/Cards%20view.md); [Views.md](https://github.com/obsidianmd/obsidian-help/blob/master/en/Bases/Views.md)
- Blender's units match studs with Unit System None and Studio's Scale Unit Stud **(read)** — [creator-docs art/blender.md](https://github.com/Roblox/creator-docs/blob/main/content/en-us/art/blender.md)
- The project already has a cloud `.bbmodel` writer, Blender sheet scripts (`design_sheet.py`, `ladder_sheet.py`) and the Open Cloud upload route **(repo)** — [tools/blockbench/to_bbmodel.py](/home/user/Roblox-Alien-Game/tools/blockbench/to_bbmodel.py); [tools/blender/](/home/user/Roblox-Alien-Game/tools/blender)

### Inferences
The workflow, step by step (each step names the tool and the file it touches):
1. **Style bible first (Obsidian).** One note, `06-art-pipelines/Blocky-Style.md`, with the seven rules of key question 3, the bevel and cube budget table of key question 2 and a rarity ladder table (cubes, height in studs, VFX per tier). Its do/don't examples are drawn once in Claude Design and the PNGs stored in `refs/`.
2. **Spec note per asset (Obsidian).** Created from a template with the frontmatter of key question 4 and a parts table in studs; `status: concept`.
3. **Concept board (Claude Design).** One canvas per world: for each species, the four orthographic views drawn as SVG on a stud grid from the parts table, the palette with roles, the face pixel grid, the greyscale silhouette strip, and the tier ladder (same base, added blocks, height steps, emissive overlay). Two or three options per species, as the help centre advises; Ethan comments on the board. The picked option's numbers go back into the note; `status: board`, `board:` set to the artboard URL.
4. **Build (Blender).** A cloud worker reads the note's parts table and builds with headless bpy (cubes, bevels only on main masses, one material per slot or a 16 px-per-stud texture), renders the four orthographic views and a three-quarter view at the sheet's scale, computes silhouette IoU per view against the board's PNG export, and writes `cubes`, `tris` and the render links back to the note; `status: build`.
5. **Review (all three).** The renders are uploaded onto the same Claude Design canvas next to the sheet (side by side at the same size); verdicts go in the note's Reviews list, one dated line each; lasting lessons move to the style bible. `status: review`, then `approved` on Ethan's yes.
6. **Ship.** Only an approved note's GLB is exported to `assets/models/<Id>/` and uploaded; its data row cites the note.
- The same six steps fit props (a sheet with pivot and kit grid), UI screens (the board is the existing mockup canvas; the build is Luau from `Theme`) and worlds (a palette and landmark board; the build is the map pass), which is how "every design passes through all three" holds without a separate process per asset type.
- Cost control: one canvas per world rather than per species keeps Claude Design usage inside plan limits; the board is redrawn only when the spec's numbers change.

- None of steps 3 to 5 has been run on a blocky species yet; the IoU check, the SVG sheet generation from a parts table and the side-by-side upload are untested.
- Whether Claude Design can render 30 species' sheets on one canvas without hitting usage limits is unknown; the plan Ethan holds is not recorded in the repo.
